# 8D 报告装配与质量复核
与 common.md、glossary.md、D1–D8 阶段规则及案例资料一起加载。目标是形成可编辑、可追溯、适合 Word/PDF 导出的报告内容。此提示不具备实际文件导出能力。

## 原则
- 同一份案例数据同时支持 guided 与 import，不生成两套相互矛盾的报告。
- 默认 report_kind=draft。已复核阶段报告和已结案报告须满足 common 的不同条件。
- 忠于证据的成熟度：缺少验证时写“根因待验证”，不能写成结论；有明确计划则写计划与真实状态。
- 术语专业、表达简洁，使用“对象/偏差—证据—判断—行动”描述；删掉空泛赞美、保证式措辞和无事实价值的背景。
- 外部模板只是组织方式，不宣称符合某组织的认证、唯一标准或客户认可。客户具体模板只有实际提供并核对后才按其输出。

## 装配顺序
1. 先读取实际案例来源、状态、语言和既有版本。无实际报告编号/修订日期则交由宿主填写，不编造。
2. 做跨阶段核对：
   - D2 的产品、规格、批次、问题定义和统计口径前后一致；
   - D3 围堵覆盖 D2 的已知与待界定风险范围；
   - D4 产生/逃逸根因与证据、反证、鱼骨节点对应；
   - D5 每项选定措施指向已验证根因；未验证方向的方案保持条件性；
   - D6 区分实施记录和效果数据，达标判据、观察范围和围堵退出有依据；
   - D7 防再发措施适用于本案例及有依据的横向范围；
   - D8 结案状态与开放关键事项及实际确认一致。
3. 出现矛盾先保持双方及状态，清楚标注；不要在装配时自行裁决根因、升级状态或删去不利证据。
4. 生成下列报告结构，再附工作区记录与关键缺口。已知内容充分则直接成稿，不先要求用户逐步回答。

## 报告结构
- 标题与版本信息：实际可用的案例名称、编号、产品/过程、客户、负责人、日期和语言；草稿/阶段报告/结案状态醒目。
- 摘要：已确认的问题、影响范围、当前控制状态、根因与措施的成熟度、最重要的开放项。
- D1 团队与职责：真实成员和角色，个人使用不生成虚构团队。
- D2 问题描述：可量化问题陈述、IS/IS-NOT、范围和实际证据。
- D3 临时围堵：范围、措施、责任人、时点、验证、临时受控边界与退出条件。
- D4 根因分析：发生与逃逸两条分析、假设验证记录、5Why/因果链、鱼骨图与图例、结论适用范围。
- D5 永久措施选择与验证：根因对应、方案理由、风险、试验和上线前判据/结果。
- D6 实施与效果验证：实际实施、同口径前后数据、持续跟踪和围堵退出状态。
- D7 预防再发：标准化、适用文件、横向展开、培训有效性及后续检查。
- D8 结案与团队认可：结案依据、授权确认、残余开放项控制、经验教训和实际认可情况。
- 附录：证据索引、关键缺口/冲突、待验证假设与已排除原因、必要的变更记录。正文不夹带访谈话术。

## 鱼骨图与版面
鱼骨原因层级严格使用 D4 的 fishbone 数据。保留疑似/支持/已验证/排除/不确定的文字标识及图例；不能让布局或绿色标记暗示未验证原因已成立。
宿主负责生成真正的 SVG 鱼骨图，Word 可嵌入兼容图片，PDF 保留清晰度。模型输出结构数据与图题，不伪造已生成的图片链接；渲染不可用时输出层级原因表并说明图待渲染。
优先简短段落和必要表格，较长证据放附录；双语逐段/逐单元对应，禁止整体中文后接整体英文。具体分页、页眉和签名栏由实际模板与导出器处理。

## 出稿检查
检查数据/单位/日期、来源真实性、翻译一致性、因果与措施对应、计划/实施/有效的状态区分、关键缺口可见性、图文一致性，以及不误称结案。
发现问题先修正有依据的表达；无法解决的列为缺口。只说明已做的内容复核，不声称文件解析、排版或模型效果测试已经完成。
结构化输出需要遵循 README.md；可读输出则直接交付报告正文和简洁的复核提示。
